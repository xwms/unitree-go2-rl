# 训练吞吐波动排查：stair_cache 的 CPU/GPU 同步

> 日期：2026-11-16　修复提交：`138925c`　文件：`src/go2_stair/go2_stair/tasks/locomotion/mdp/stair_cache.py`

## 问题

Stage2 训练吞吐频繁波动。他人协助修复后定位：旧版 stair_cache 在运行中"CPU 与 GPU 之间来回切换约 3 万次"——即约 3 万次强制同步，每次都打断 GPU 流水线。

## 分析

旧代码有三处强制 GPU→CPU 同步（读回 GPU 张量的值必然停流水线）：

1. **每步的缓存过期检查**：`torch.equal(cache["levels"], levels)` 比较两个 GPU 张量，必须拷回 CPU。Stage2 每个 env step 至少 2 次调用。
2. **课程升级触发重建时的逐环境循环**（"3 万次"的主体）：`int(levels[e])`、`int(types[e])`、`origins[e]` 对 GPU 张量逐个取标量，每环境约 3 次同步 × 8192 环境 ≈ 2.5 万次/重建。训练早期课程频繁升级，且每次 resume 课程重置后重新爬级，重建反复发生。
3. **投影的逐 tile 循环**：`nonzero()` 后 `len(env_ids)` 每 tile 每步一次同步。

每次同步 = GPU 清空排队任务、拷数据回 CPU、再起步，collection 阶段因此频繁"急刹车"。

附带查证（排除正确性疑虑）：

- 旧版按 tile 缓存几何、取同 tile 第一个环境的 origin。查 isaaclab 2.3.0 源码（`terrain_importer.py::_compute_env_origins_curriculum`）：curriculum 模式 `env_origins = terrain_origins[levels, types]`，**同 tile 环境 origin 完全相同**，故旧版在真实系统中结果正确。
- 注册表 centerline 为 float64 numpy，`torch.as_tensor(..., float32)` 因 dtype 不同会拷贝，旧版的原地 `+=` 不污染共享元数据。

## 解决

思路：能不问就不问，要问就一次问完。

- **静态 GPU 查表**：启动时在 CPU 上一次填完全部 tile 的几何表（线段补齐到统一形状 + valid 标记），一次 `.to(device)` 上 GPU。全程仅 1 次同步。
- **每步零同步**：查询改为纯 GPU 高级索引 `table[tile_ids]`；过期检查改为比较 `id(gen_cfg)` / device（不碰 GPU 张量）。
- **投影全向量化**：所有环境 × 所有线段一次矩阵运算，空位距离设为无穷大后一次 `argmin` 选最近线段，去掉 Python 循环。

### 静态查表长什么样

建表：30 个瓦片（10 难度等级 × 3 列地形：直梯 / L 形 / 螺旋）的几何在启动时一次算好，按瓦片编号 `tid = level × 3 + type` 排成若干张并行小表，线段数统一补齐到 S 条（空位补零 + `seg_valid` 标记），最后一次性搬上 GPU：

| 表 | 形状 | 内容 |
|---|---|---|
| `is_stair_tbl` | (30,) | 该瓦片是楼梯吗（bool） |
| `goal_end_local_tbl` | (30, 3) | 楼梯顶端的局部坐标 |
| `goal_dir_tbl` | (30, 2) | 目标朝向 |
| `spawn_offset_tbl` / `spawn_yaw_tbl` | (30, 3) / (30,) | 出生点偏移、朝向 |
| `platform_z_tbl` 等金字塔参数 | (30,) | 金字塔平台高度/半径/台阶参数（楼梯瓦片为 0） |
| `seg_a_local` / `seg_b_local` | (30, S, 2) | 每条线段的起/终点 |
| `cum_arc` | (30, S+1) | 累计弧长 |
| `seg_valid` | (30, S) | 哪些线段有效（bool） |

查表：每一步只是"按编号取行"，数据不出 GPU：

```python
tile_ids = levels * num_cols + types      # 每个环境当前在哪个瓦片
is_stair = is_stair_tbl[tile_ids]         # 查：是楼梯吗
end_w    = goal_end_local_tbl[tile_ids] + origins   # 查：目标点（+环境原点）
```

整张表只有几千个浮点数，显存占用可忽略。

## 验证

本地 /tmp 临时 venv（CPU torch）+ 合成元数据 + fake env，加载新旧两模块对比，共 6 个场景：8192 环境随机分配、课程变化触发重建、全金字塔、全楼梯、元数据不被污染、同 tile 内 origin 分叉（非 isaaclab 模式）。

结果：

- 真实场景下 11 个缓存字段 + `robot_default_z` + 投影 arc/lat **逐位一致**；
- 唯一差异仅出现在"同 tile 环境 origin 不同"的非 isaaclab 模式下（已确认真实系统不会出现；新版按环境取 origin，写法更稳）；
- 云端下次起训即用新代码，吞吐波动是否消除待实测确认。
